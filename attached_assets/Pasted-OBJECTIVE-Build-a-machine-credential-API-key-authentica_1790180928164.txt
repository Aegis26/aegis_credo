OBJECTIVE
Build a machine-credential / API-key authentication system for Credo so that 
the OMG Workflow System can safely authenticate and call Credo endpoints 
without using a human user session.

CONTEXT
- Credo is multi-tenant (organizations)
- OMG Workflow System needs to read/write financial data to OMG's Credo org
- Currently, Credo only supports session-cookie auth (user-based)
- Need: Bearer token auth + organization-scoped API keys + scope-based permissions

REQUIREMENTS

1. MACHINE CREDENTIALS TABLE
   Create `machine_credentials` table:
   - id (UUID)
   - organization_id (FK to organizations)
   - name (string) — "OMG Workflow System"
   - api_key (encrypted) — generated key
   - api_key_hash (string) — hash for lookups (don't store plaintext)
   - scopes (JSON array) — e.g., ["read:invoices", "write:invoices", "read:gl"]
   - is_active (boolean)
   - created_at (timestamp)
   - last_used_at (timestamp)
   - revoked_at (timestamp, nullable)
   - created_by (user_id)
   - notes (text)
   - Indexes: organization_id, api_key_hash, is_active

2. BEARER TOKEN AUTHENTICATION MIDDLEWARE
   Add auth middleware to Express:
   - Extract "Bearer {token}" from Authorization header
   - Hash the token, lookup in machine_credentials
   - Verify: is_active = true, revoked_at = null, organization_id matches request
   - Attach { principal: "machine", credential_id, organization_id, scopes } to req
   - Return 401 if invalid/revoked/expired

3. SCOPE-BASED AUTHORIZATION
   Define scopes for OMG:
   - read:invoices — GET /api/organizations/:orgId/invoices
   - write:invoices — POST /api/organizations/:orgId/invoices
   - read:gl — GET /api/organizations/:orgId/gl_entries
   - write:gl — POST /api/organizations/:orgId/gl_entries
   - read:reports — GET /api/organizations/:orgId/reports

   Implement scope check in handlers:
   - If req.principal.scopes includes required scope → allow
   - Else → 403 Forbidden

4. API KEY MANAGEMENT ENDPOINTS (Credo dashboard)
   POST /api/organizations/:orgId/credentials
   - Create new API key for this org
   - Return: { api_key, name, scopes, created_at }
   - Visible only to org owners

   GET /api/organizations/:orgId/credentials
   - List all active/revoked keys for this org
   - Show: name, scopes, created_at, last_used_at, status

   DELETE /api/organizations/:orgId/credentials/:credentialId
   - Revoke (soft delete: set revoked_at)
   - Cannot be un-revoked

   POST /api/organizations/:orgId/credentials/:credentialId/rotate
   - Generate new key, revoke old one
   - Return new key (only shown once)

5. AUDIT LOGGING
   Log to `audit_logs` table:
   - Who created the credential (user_id)
   - When (created_at)
   - What scopes were granted
   - Every API call using the credential (principal_id, endpoint, status, timestamp)
   - Revocation events

7. SECURITY CHECKLIST
   - Never log or display full API key (except once on creation)
   - Hash stored in DB, compare on lookup
   - API keys are org-scoped (credential.organization_id is immutable)
   - Scopes are checked on every request
   - Revocation is immediate (no caching)
   - Audit every credential operation + API call

8. TESTING
   - 20+ tests covering:
     * Create credential → get valid API key
     * Call endpoint with valid key + correct scope → 200
     * Call endpoint with valid key + missing scope → 403
     * Call endpoint with revoked key → 401
     * Call endpoint for different org → 403
     * Rotate key → old key returns 401, new key works
     * Revoke key → immediate 401
   - Browser test: create key, revoke, verify dashboard updates
